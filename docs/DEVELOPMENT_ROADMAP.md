# План разработки (Roadmap)

Каждый этап завершается проверкой. Функция считается готовой только после её фактической проверки (правило 9 проекта). Оценки длительности ориентировочные и рассчитаны на одного разработчика с помощью агента.

| Этап | Название | Зависит от | Оценка | Статус (2026-11-06) |
|---|---|---|---|---|
| 1 | Репозиторий и структура | — | 1 день | Готово |
| 2 | База данных | 1 | 1–2 дня | Готово (Neon, без локального Docker) |
| 3 | Подключение реальных источников | 2 | 2–3 дня | Готово, см. findings/firms_schema_check.md |
| 4 | Механизм получения и обновления | 3 | 2–3 дня | Готово: сбор по расписанию, погода, очаги, бэкап, замена NRT на SP |
| 5 | Backend API | 2, 4 | 3–4 дня | Заменено чтением БД из Next.js (ADR-5) |
| 6 | ML-модель | 3, 4 | 5–8 дней | Готово: модель 1.0.0 `active` (PR-AUC test 0,675), см. ml/models/1.0.0/evaluation.md |
| 7 | Подключение frontend к данным | 5, дизайн | 2–3 дня | Готово (дизайн Thermal Glass) |
| 8 | Интерфейсные модули | 7 | 6–9 дней | Частично: основные экраны есть, доработки по списку владельца |
| 9 | Тестирование | 5, 8 | 2–3 дня (и непрерывно) | Частично: юнит-тесты pipeline, CI |
| 10 | Деплой и публикация | 9 | 1–2 дня | Ждёт решения владельца (Vercel) |

Этапы 6 (ML) и 7–8 (frontend) можно вести параллельно после этапа 5. Дизайн в Claude Design делается параллельно этапам 2–5.

---

## Этап 1. Подготовка репозитория и структуры
**Задачи:** монорепозиторий, линтеры и форматтеры, pre-commit (ruff, black или ruff-format, mypy, eslint, prettier, gitleaks), базовый CI, `.env.example`, README.
**Файлы:** `README.md`, `LICENSE`, `.gitignore`, `.env.example`, `.pre-commit-config.yaml`, `pyproject.toml` (workspace), `api/`, `pipeline/`, `ml/`, `shared/`, `web/` (каркас Next.js), `.github/workflows/ci.yml`, `docs/`.
**Технологии:** Git, GitHub, Python ≥ 3.12 (CI и Render: 3.12), pip + venv, Node.js 24 LTS, npm, Next.js 16.
**Проверка:** `pre-commit run --all-files` проходит, CI зелёный на пустом каркасе, gitleaks ловит тестовую строку-ключ во временной ветке.
**Готово, когда:** CI зелёный, структура соответствует ADR-7.

## Этап 2. Настройка базы данных
**Задачи:** локальный PostGIS в Docker (`docker-compose.yml`), Alembic, все таблицы, индексы, ограничения, представления из DATABASE_SCHEMA, роли, загрузка регионов из открытого набора границ, проект Neon.
**Файлы:** `db/migrations/versions/*.py`, `db/roles.sql`, `docker-compose.yml`, `pipeline/load_regions.py`, `.github/workflows/migrate.yml`.
**Технологии:** PostgreSQL, PostGIS, Alembic, SQLAlchemy.
**Проверка:** `alembic upgrade head` и `downgrade base` работают на чистой БД. CHECK-ограничения отклоняют некорректные строки (тест). `EXPLAIN` типовых геозапросов показывает использование GiST-индекса.
**Готово, когда:** схема развёрнута локально и в Neon, регионы загружены, роли разграничены.

## Этап 3. Подключение реальных спутниковых источников
**Задачи:** получить MAP_KEY. Клиент FIRMS (Area API, `data_availability`), разбор CSV VIIRS и MODIS, Pydantic-схемы, нормализация, обработка ошибок и лимитов. Клиент Open-Meteo (archive и forecast). **Первая реальная выгрузка по AOI**: сверить имена колонок, коды спутников, формат `acq_time` и поведение версий NRT. Оценить годовой объём для бюджета БД.
**Файлы:** `pipeline/sources/firms.py`, `pipeline/sources/openmeteo.py`, `pipeline/validate.py`, `pipeline/normalize.py`, `shared/schemas.py`, `tests/pipeline/fixtures/` (только **синтетические** строки для тестов), `docs/findings/firms_schema_check.md`.
**Технологии:** httpx, tenacity, pydantic, pandas.
**Проверка:** интеграционный тест (ручной, с реальным ключом) получает данные за 1 день. Юнит-тесты разбора проходят на синтетических фикстурах. Отчёт по фактической схеме лежит в `docs/findings`.
**Готово, когда:** все ⚠ по FIRMS из DATA_SOURCES подтверждены или исправлены по реальным данным.

## Этап 4. Механизм получения и обновления данных
**Задачи:** оркестратор `pipeline.run`, журнал запусков и fetch'ей, идемпотентный upsert, история версий, привязка регионов, кластеризация, погодное обогащение по ячейкам, обновление `mv_daily_stats`, политика хранения, контроль размера БД. Workflow `ingest.yml` (каждые 30 минут), `backfill.yml`, `backup.yml`.
**Файлы:** `pipeline/run.py`, `pipeline/load.py`, `pipeline/enrich.py`, `pipeline/retention.py`, `.github/workflows/{ingest,backfill,backup}.yml`.
**Технологии:** SQLAlchemy Core, PostGIS (`ST_ClusterDBSCAN`, `ST_Intersects`), GitHub Actions.
**Проверка:** двойной запуск на одних и тех же данных не меняет число строк. Имитация ошибки источника даёт статус `partial`. 24 часа работы по расписанию без ручного вмешательства. Выборочная сверка 10 записей с FIRMS.
**Готово, когда:** данные обновляются автоматически ≥ 24 часа, журнал корректен.

## Этап 5. Backend и API
**Задачи:** FastAPI-приложение со всеми эндпоинтами из API_SPECIFICATION, блок `meta`, валидация параметров, ошибки, rate limit, CORS, кэш-заголовки, структурные логи, OpenAPI. Замер холодного старта на Render и сравнение с Vercel Python (ADR-5).
**Файлы:** `api/app/main.py`, `api/app/routers/{detections,stats,sources,model,regions,export,health}.py`, `api/app/db.py`, `api/app/schemas.py`, `api/tests/`.
**Технологии:** FastAPI, Pydantic, SQLAlchemy, slowapi, pytest, httpx (TestClient).
**Проверка:** тесты на изолированной тестовой БД с синтетическими данными покрывают каждый эндпоинт, ошибки и пустые результаты. Ручная сверка `/stats/summary` с SQL на реальной БД. Время ответа `/detections` (2 000 точек) ≤ 1,5 с на тёплом сервере.
**Готово, когда:** API развёрнут на Render, все эндпоинты отвечают на реальных данных.

## Этап 6. Создание и проверка ML-модели
**Задачи:** выгрузка архива VIIRS по AOI (2019–2025), загрузка MCD64A1, разметка, расчёт признаков (только прошлое), погода из архива, baseline'ы, сравнение LR, RF, XGBoost и LightGBM, подбор гиперпараметров на временной и пространственной CV, калибровка, финальная оценка на test, отчёт, карточка модели, регистрация, скоринг в pipeline. При невыполнении критериев допуска модель получает статус `rejected` и система работает без ML.
**Файлы:** `ml/build_dataset.py`, `ml/labels.py`, `ml/features.py` (**общий** с `pipeline/score.py`, чтобы обучение и инференс считались одинаково), `ml/train.py`, `ml/evaluate.py`, `ml/register.py`, `ml/reports/<version>/`, `pipeline/score.py`, `.github/workflows/train.yml`.
**Технологии:** pandas, geopandas, rasterio, earthaccess, scikit-learn, lightgbm, xgboost, optuna, shap.
**Проверка:** тест на отсутствие утечки (признаки по объекту t не зависят от данных после t). Воспроизводимость (повторное обучение с тем же seed даёт идентичные метрики). Отчёт сгенерирован автоматически. Ручная визуальная проверка 50 случаев разметки.
**Готово, когда:** отчёт `evaluation.md` опубликован, решение `active` или `rejected` принято по критериям ML_STRATEGY §8.

## Этап 7. Подключение frontend к API
**Задачи:** внедрение дизайн-токенов и компонентов из Claude Design, генерация TS-типов из OpenAPI, API-клиент, TanStack Query (повторы, кэш), глобальные состояния (холодный старт, ошибка, устаревшие данные, пусто), синхронизация фильтров с URL.
**Файлы:** `web/src/lib/api/{client.ts,types.gen.ts}`, `web/src/components/states/*`, `web/src/components/layout/*`, `web/tailwind.config.ts`, `web/src/styles/tokens.css`.
**Технологии:** Next.js, TypeScript, Tailwind, shadcn/ui, TanStack Query, openapi-typescript.
**Проверка:** при остановленном API каждый экран показывает ошибку, а не нули. Типы компилируются без `any` в API-слое.
**Готово, когда:** каркас всех страниц получает реальные данные, состояния работают.

## Этап 8. Реализация интерфейсных модулей
**Задачи:** дашборд, карта (MapLibre: кластеры, сетка, слои, фильтры, popup, таймлайн, режим «Список»), детальная страница, потенциальный очаг, аналитика (7 секций), источники, модель, о системе, тёмная и светлая тема, адаптивность, доступность. Опционально: dNBR по Sentinel-2.
**Файлы:** `web/src/app/{page.tsx,map,detections/[id],clusters/[id],analytics,sources,model,about}/…`, `web/src/components/{map,charts,cards,filters}/*`.
**Технологии:** MapLibre GL JS, Recharts, shadcn/ui.
**Проверка:** чек-лист UI_UX_SPECIFICATION по каждому экрану в 6 состояниях. Lighthouse (performance ≥ 80 на desktop, accessibility ≥ 90). Проверка на ширине 360 px.
**Готово, когда:** все экраны соответствуют ТЗ и работают на реальных данных в preview-деплое.

## Этап 9. Тестирование
**Задачи:** юнит- и интеграционные тесты pipeline и API (покрытие ≥ 70 %), e2e (Playwright) ключевых сценариев, тест-«сторож» отсутствия тестовых данных в рабочей БД, нагрузочный smoke (k6 или locust: 20 RPS на `/detections`), проверка отказоустойчивости (недоступность FIRMS, БД, неверный ключ), проверка безопасности (секреты, CORS, rate limit, SQL-инъекции через параметры).
**Файлы:** `tests/`, `api/tests/`, `web/e2e/*.spec.ts`, `tests/load/`.
**Технологии:** pytest, pytest-cov, Playwright, k6.
**Проверка:** все тесты зелёные в CI, отчёт покрытия.
**Готово, когда:** выполнены критерии ACCEPTANCE_CRITERIA (разделы «Качество» и «Надёжность»).

**Задачи:** финальный деплой по DEPLOYMENT_PLAN, README (описание, скриншоты реальных экранов, архитектура, запуск локально, атрибуция), релиз `v1.0.0`, smoke-checklist, подготовка к демонстрации («пробуждение» API, проверка свежести данных).
**Файлы:** `README.md`, `CHANGELOG.md`, `docs/DEMO_CHECKLIST.md`.
**Проверка:** smoke-checklist DEPLOYMENT_PLAN §3 шаг 7 пройден в продакшене.
**Готово, когда:** система доступна по публичному URL, данные обновляются автоматически, все критерии приёмки выполнены.
