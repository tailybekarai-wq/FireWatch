# Требования

Обозначения: **FR**: функциональное требование, **NFR**: нефункциональное, **DR**: требование к достоверности данных. Приоритет: M (Must, обязательно для MVP), S (Should, желательно), C (Could, при наличии времени).

## 1. Требования к достоверности данных (DR)

| ID | Требование | Приоритет |
|---|---|---|
| DR-1 | Все данные в UI поступают только из БД, наполняемой реальными внешними источниками | M |
| DR-2 | Запрещены фиктивные маркеры, координаты, статистика, seed-файлы с «пожарами» в рабочей БД и в демо | M |
| DR-3 | Синтетические данные допустимы только в автотестах с изолированной тестовой БД (отдельный контейнер). CI проверяет, что в рабочей БД нет записей тестового источника | M |
| DR-4 | У каждой записи обнаружения хранятся: источник, официальный URL, время наблюдения (UTC), время получения, тип данных, координаты, статус обработки, ID запуска загрузки | M |
| DR-5 | Если источник недоступен, UI показывает ошибку, время последнего успешного обновления и не подставляет значения | M |
| DR-6 | Каждый API-ответ содержит блок `meta.freshness`: время последнего успешного обновления по источникам | M |
| DR-7 | Обнаружение никогда не маркируется как «подтверждённый пожар» без поля `confirmation_source` | M |
| DR-8 | ML-метрики в UI берутся только из таблицы `ml_model_versions`, заполняемой скриптом оценки. Ручной ввод метрик запрещён | M |
| DR-9 | Погода отображается как фактор пожарной опасности, а не как доказательство пожара | M |

## 3. Нефункциональные требования

| ID | Требование | Приоритет |
|---|---|---|
| NFR-1 | Стоимость эксплуатации MVP: 0 $ (бесплатные тарифы) | M |
| NFR-2 | Задержка от публикации в FIRMS до появления в системе: ≤ 60 минут (определяется расписанием) | M |
| NFR-3 | Ответ API на карту (до 5 000 точек) ≤ 1,5 с при «тёплом» сервере. Холодный старт документирован как ограничение | S |
| NFR-4 | Секреты только в переменных окружения и GitHub Secrets. В репозитории есть `.env.example` без значений | M |
| NFR-5 | Логирование в формате JSON с уровнями. Ошибки внешних API логируются с кодом и временем | M |
| NFR-6 | Адаптивность: от 360 px до 4K. Карта работает на мобильных | M |
| NFR-7 | Доступность: контраст WCAG AA, управление с клавиатуры, цвет не является единственным носителем смысла | S |
| NFR-8 | Покрытие тестами backend (ingestion, API) ≥ 70 % строк | S |
| NFR-9 | Воспроизводимость ML: фиксированный seed, версия датасета, хэш кода, сохранённый артефакт | M |
| NFR-10 | Локализация UI: русский (основной), английский (C) | M |
| NFR-11 | Всё время хранится в UTC и отображается в UTC и местном времени Казахстана (UTC+5, единый пояс с 2024-03-01, зона `Asia/Almaty`) | M |
| NFR-12 | Объём БД не превышает лимит бесплатного тарифа (политика хранения, см. DATABASE_SCHEMA §6) | M |
| NFR-13 | Rate limiting публичного API, CORS только для домена frontend | M |

## 4. Пользователи и сценарии

- **Аналитик или диспетчер** открывает карту и смотрит обнаружения за 24 часа в своём регионе, сортирует по ML-оценке и открывает карточку.
- **Исследователь** выбирает период, сравнивает его с прошлым годом и экспортирует CSV.
- **Член комиссии по защите диплома** проверяет источники и модель: откуда данные, когда обновлены, как валидирована модель.
- **Администратор** (через логи, GitHub Actions и страницу источников) видит ошибки загрузки.

Учётных записей в MVP нет: все страницы доступны только для чтения.
